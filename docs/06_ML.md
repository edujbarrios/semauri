# ML semantic domain

The built-in `ml` domain is Semauri's AI-native semantic domain. It describes machine-learning intent as typed compiler semantics before any framework or accelerator runtime executes the workload.

## Current types

```text
ml.dataset
ml.model
ml.device
ml.resource_budget
ml.training_config
ml.training_run
ml.inference_run
ml.evaluation_run
```

ML runtime objects are nominal values. They are produced by semantic operations rather than forged from primitive strings.

## Dataset lineage

Datasets can be derived without executing framework code:

```text
Let dataset be Open dataset "./images".
Let normalized be Transform dataset using "normalize".
Let training be Split normalized ratio 0.8 seed 42.
```

Transforms and splits preserve the `ml.dataset` type and make lineage explicit. Split ratios must be greater than zero and less than one, and split seeds must be non-negative integers (`S340`).

## Load or construct a model

A model may come from an external identifier:

```text
Let model be Load model "resnet18".
```

or from Semauri model-construction semantics:

```text
Let model be Build cnn for 2 classes input channels 3.
```

Both produce `ml.model`, but their provenance remains different in the RuntimePlan.

## Immutable model transforms

```text
Let model be Build cnn for 2 classes input channels 3.
Let frozen be Freeze model component "features".
Let adapted be Apply lora to frozen rank 16 alpha 32.
```

Each operation produces a new typed model reference, making model lineage explicit and inspectable. QLoRA is also available through `Adapt <model> with qlora ...` with validated 4-bit or 8-bit quantization.

## Training, inference and evaluation

```text
Within ml:
  Let dataset be Open dataset "./images".
  Let model be Load model "resnet18".
  Let device be Select device "cuda".
  Let run be Train model using dataset on device for 10 epochs.
  Let inference be Infer model on dataset using device.
  Let evaluation be Evaluate model on dataset using device metric "accuracy".
End.
```

Evaluation produces an opaque `ml.evaluation_run` and declares `compute` plus `model_evaluation` effects. Literal metrics are validated at compile time; supported metrics are `accuracy`, `precision`, `recall`, `f1`, `loss`, and `perplexity`. Unsupported literal metrics report `S341`.

## Typed training configuration

For a more explicit training plan, create an opaque `ml.training_config`:

```text
Let config be Configure training for 12 epochs using optimizer "adamw" learning rate 0.0003 batch size 32 seed 42.
Let run be Fit model using dataset on device with config.
```

For precision, gradient accumulation and checkpoint cadence, use the extended `Plan training ... precision ... accumulate ... checkpoint every ...` form. Training configuration remains compiler data until a runtime consumes the plan.

## Resource-aware training

Resource constraints can be represented as compiler-visible values rather than hidden runtime flags:

```text
Let resources be Budget resources memory 24 gb workers 4.
Let run be Allocate resources to fit model using dataset on device with config.
```

`Budget resources` produces an opaque `ml.resource_budget`. Memory must be positive and worker counts must be positive integers (`S342`). The resource budget itself is a pure planning value; allocating it to a fit retains the normal `compute` and `model_training` effects.

## Inspect before execution

```bash
ruby bin/semauri plan train.sema
ruby bin/semauri effects train.sema
```

The ML domain may declare `filesystem_read`, `model_load`, `compute`, `model_training`, `model_inference`, and `model_evaluation`. Dataset/model construction, configuration and resource budgeting are pure planning operations; training, inference, evaluation and external access remain observable effects.

## Framework boundary

Semauri source describes semantic concepts rather than framework calls. A runtime may implement the same plan using PyTorch, Transformers, ONNX Runtime, OpenVINO, JAX or another system. Framework-specific behavior belongs at the explicit runtime/extension boundary.

## Direction

The ML plan continues to grow around typed concepts: model architecture and adapters, dataset provenance and transforms, training/checkpoint policy, evaluation metrics, and hardware/resource constraints. Checkpoint lineage and richer cross-resource validation remain future work.
